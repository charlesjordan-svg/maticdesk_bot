## 2. What was actually verified, with evidence

Claims below were observed, not assumed. Nothing here is inferred from code reading.

### The four primitives, elevated, on real hardware

```
restart_service  success  tier=R1   226ms   STOPPED -> RUNNING
flush_dns        success  tier=R1     1ms
renew_dhcp       success  tier=R1  4401ms   release+renew rc=0, kept 192.168.50.223
reset_adapter    success  tier=R2  3033ms   Ethernet down->up, back on 192.168.50.223
```

All four are native Win32 calls. **No `cmd.exe`, no `powershell.exe`, no `sc.exe`/`netsh`, no
encoded command strings** (§6, §12). Bindings via `koffi`, which ships prebuilt binaries — no
node-gyp, no build toolchain.

### The safety invariants

- **Off-enum parameter rejected** before any Win32 call: `serviceName: "spooler; calc.exe"` →
  refused by schema validation.
- **Unknown capability rejected**: `format_disk` → "not in the catalog".
- **Consent tokens are single-use** and **bound to a proposal hash** — a token minted for
  `flush_dns` will not execute `restart_service`, and cannot be replayed.
- **Execution with no token does nothing**, and is still audited.
- **ERROR_ACCESS_DENIED surfaces as "this needs the privileged broker"**, never as a user error
  (§12). Verified unelevated on both the SCM and the adapter API.
- **34+ audit records** written across successes, refusals and denials.

### Voice

Piper loads once at startup (~4 s for the 63 MB ONNX) and is kept warm as a persistent worker;
per-utterance synthesis is fast. Visemes drive off `audio.currentTime`, verified by screenshot
mid-speech. Voice failure degrades to text-plus-mouth-animation and never blocks a reply.

## 3. Findings that changed the plan

### `dnscache` cannot be restarted — §6 catalog was wrong

The DNS Client service does not accept stop requests on Windows 10/11. Verified on this machine:
`controlsAccepted` is `0x58`, with `SERVICE_ACCEPT_STOP` clear. `restart_service("dnscache")` can
never succeed.

The broker refuses it by policy with that explanation, enforced from **observed state** (any
service reporting `RUNNING` with `SERVICE_ACCEPT_STOP` clear) and not only from a static list.
DNS symptoms route to `flush_dns` instead.

This is a good demo beat: the model proposes, the broker declines on policy grounds and explains
why — which shows the model is not in charge.

### `reset_adapter` uses `SetIfEntry`, not WMI/`INetCfg`

§6 specifies WMI/`INetCfg`. Implemented instead with `iphlpapi!SetIfEntry`, writing only
`dwAdminStatus` (1 = UP, 2 = DOWN). Same disable-then-enable effect, native, and no COM/VARIANT
marshalling to get wrong on a four-day clock. Verified working on the Intel I225-V.

`TODO(phase1)`: confirm coverage across fleet NIC drivers. `SetIfEntry` can return
`ERROR_NOT_SUPPORTED` on some virtual adapters, where `INetCfg` is the more general answer. On
this NIC it returned error 5 (privilege), not 50 (unsupported), so the API is accepted here.

### `strict: true` rejects `minimum` (cost ~40 minutes of debugging)

Strict tool schemas accept only a restricted JSON Schema subset. `renew_dhcp`'s `adapterIndex`
carried `"minimum": 0`, producing:

```
400 invalid_request_error
tools.2.custom: For 'integer' type, property 'minimum' is not supported
```

`strict` itself is fine on `claude-haiku-4-5`; the combination with `minimum` is not. The wire
schema is now sanitized by `strictSafeSchema()`, which recursively strips `minimum`, `maximum`,
`pattern`, `format` and the other non-strict keywords. **The catalog keeps the full schema and the
broker still enforces it** (`adapterIndex: -1` is rejected), so the constraint moved to the layer
allowed to express it rather than disappearing.

**Process lesson worth carrying forward:** two fixes were attempted by guessing before the actual
error was read. The API's own message named the offending tool *and* keyword immediately. The app
now logs it as `[cloud] API <status> <type>: <message>` in the dev-log panel — **read that first.**

### Tier-0 keyword matching was too brittle for unscripted speech

The router matched fixed phrases, so *"cannot connect to anything"* — a completely natural thing
to say — matched nothing and produced **no proposal at all**. Since tier-0 is both the
differentiator and the fallback when the API fails live, this was a real stage risk.

Now matches short stems (`connect` covers cannot/can't/connection/disconnected/connecting), with
**printer ordered ahead of network** so "I can't connect my printer" resolves to the spooler.
16 natural phrasings are locked in by tests.

### The virtual-adapter trap (caught by tests)

Tier-0 originally proposed `renew_dhcp` on a Bluetooth PAN adapter, because "DHCP-enabled with no
IP" describes a permanently-idle virtual adapter as well as an unplugged Ethernet port. The router
now gates candidates on link state (`GetIfEntry` → `dwOperStatus`) and returns the online case to
`flush_dns` before considering adapter surgery. Regression-tested.

## 4. Architecture

```
src/
  broker/
    broker.d.ts            THE contract. Demo: InProcessBroker. Phase 1: NamedPipeBroker.
    in-process-broker.js   validate -> mintConsentToken -> execute, + audit
    schema.js              parameter validation (the §5 invariant lives here)
    catalog.json           four capabilities + policy
    capabilities/index.js  the four primitives + the unprivileged probe
    win32/{scm,net}.js     native bindings. PRIVILEGED - broker-only imports
  router/tier0.js          local deterministic router; runs BEFORE any cloud call
  agent/
    agent.js               unprivileged. tier-0 first, cloud second
    cloud-client.js        Anthropic client; tool surface generated FROM the catalog
  main/                    Electron main, preload, Piper worker management
  renderer/                UI + avatar + viseme driver (no broker logic)
```

**`src/main/main.js` is the only file that names a broker implementation.** Swapping
`InProcessBroker` for `NamedPipeBroker` there is the entire Phase 1 change at the call sites (§2).

The cloud client's **tool surface is generated from `catalog.json`** — one tool per capability,
named after the capability id. The catalog stays the single source of truth, and the model is
structurally unable to name a capability that is not in it.

## 5. Run and test

```bash
npm install
npm run start:elevated      # or `npm.cmd start` from an already-elevated shell
npm test                    # 41 checks, headless
npm run verify:privileged    # elevated; the gate on the §9 core. -IncludeNetwork adds R2
npm run test:cloud          # diagnoses any cloud/API error, bisects the tool set
npm run inject-fault -- -Fault printer   # or network | dhcp | sound
npm run reset-demo
```

Two environment gotchas on this machine:

- **PowerShell execution policy blocks npm's `.ps1` shim.** Use `npm.cmd`, which needs no policy
  change. (Bash/`npm.cmd` was why this never appeared during development.)
- **`python` is not on PATH; `py -3` is.** Already handled in `config.json`.

### The API key

Put it in a gitignored `.env` in the project root:

```
ANTHROPIC_API_KEY=sk-ant-...
```

**Use the file, not a session variable.** Elevation via `RunAs` starts a new process that does
**not** inherit session environment variables, so a key exported in an ordinary shell never
reaches the elevated app — it silently drops to tier-0 only. The startup log states the source:
`[cloud] claude-haiku-4-5 ready (key from .env file)`.

Without a key the app still runs: Scenarios 1 and 2 work entirely on the tier-0 router, and the
UI says the cloud is unavailable.

## 7. Honesty ledger (§13)

Everything below is stubbed or unverified and marked `TODO(phase1)` in code. The audience is a
technical IT lead; the demo must not imply more than exists.

- **Catalog signature verification is stubbed.** `verifyCatalogSignature()` logs this loudly at
  startup. An unsigned catalog is the whole trust root of the privileged half.
- **The audit log is a file beside the app**, not a location the user cannot modify, and is not
  shipped anywhere.
- **No named pipe, no Windows Service.** Single elevated process (§11).
- **The escalation payload is shown, never sent.** There is no ITSM integration and the UI says so.
- **`strict: true` schema constraints are sanitized on the wire** (see §3) — enforcement is the
  broker's validator, not the API.
- **No performance claims are made anywhere.** The timings in this document are single
  observations from one machine, recorded for engineering purposes, not benchmarks.

`docs/BROKER-SURFACE.md` is current and is the allowlisting document (§12): every native API,
service, and registry key the privileged half touches. Registry keys touched: **none**.
