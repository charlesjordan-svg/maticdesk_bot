# Phase 1 — Plan

**Date:** 2026-09-03
**Register:** D161 is current. Numbering below cites register IDs.
**Scope basis:** D149 (endpoint is phase one; hub-distributed privileged content is phase two),
D133, D130, `client/docs/2026-09-03-consent-protocol-design.md`.

---

## 0. What Phase 1 is

Two tracks that ship together and can be built in parallel after the first item.

**Track A — the endpoint split.** `broker.d.ts` states it: the demo ships `InProcessBroker` in one
elevated process; Phase 1 ships `NamedPipeBroker` — an unprivileged agent talking to a privileged
Windows Service. This is the change that makes the product installable on a fleet where users have
no local admin.

**Track B — the phase-one hub.** D149's scope: identity, inference proxy, audit ingestion, ticket
store, KB retrieval, outbound email. **Not** catalog distribution, per-tenant catalogs, release
channels or a tenant policy engine — the four primitives ship as a frozen vendor-signed bundle
inside the MSI.

**Consequence worth stating plainly:** because nothing privileged moves over the wire in Phase 1,
**H1, H4 and H6 have nothing to bite on yet.** They are Phase 2 invariants. H3e, H5 and the new
consent rule are the Phase 1 ones.

---

## 1. The one hard ordering constraint

**A0 must complete before A1 starts.** The two-step consent protocol changes the broker contract
from `execute(proposal, token)` to `execute(nonce)`. Consent becomes a two-step exchange. Writing
the pipe protocol first and retrofitting this is the expensive version, and the reason is structural
rather than aesthetic: the substitution demonstrated in `CONSENT-SURFACE-2026-09-03.md` only closes
if the broker retains the proposal, which means the protocol has to carry a nonce rather than a
proposal at approval time.

Everything else in Track A can reorder. Track B has no dependency on Track A at all.

## 5. What gates what

**Blocking now:**

- **The embedder.** D144 decided the direction (one self-hostable permissively-licensed model, run by
  us in managed mode and by the customer in self-hosted). The actual model is unpicked, and B7 cannot
  start. Deciding constraint: **one model must serve both deployment modes**, or a customer can never
  be migrated between them without a full re-embed. Also needs `[VERIFY]` on ONNX Runtime on
  ARM/Graviton — the one item that could change the pick outright.
- **`[VERIFY]` on the WTS APIs** for A4. Cited from memory in the review, never retrieved from
  primary documentation.

**Blocking shipping, not building:**

- **OPEN-8, build-pipeline integrity.** With standalone confirmed, a vendor-signed installer has
  automatic reach to those endpoints. Separate signing identities for catalog and binaries, two-party
  release approval, reproducible builds, a release transparency log. Blocks standalone GA, not
  development.
- **The DPA and subprocessor list, and end-user notice text** (D127's session-start disclosure, which
  still has no wording). External lead time. Start early.

**Blocking the Phase 1 exit criteria but not the work:**

- **The top-30 ticket categories.** Outstanding since early August. It is the measurement baseline
  for every metric in Track C and the load-bearing assumption behind the whole privileged half. Phase
  1 can be built without it; Phase 1 cannot be *evaluated* without it.

## 6. Effort and the honest number

**I am not producing a total.** The review decomposed one Track B item at 6–8 engineer-weeks against
an aggregate that implied 2, and D149 then removed two of six components. Those pull in opposite
directions and the previous estimate has already been wrong once.

What can be said:

- **B3 alone is 6–8 engineer-weeks** on the review's decomposition.
- **A0 is small** — days — and it unblocks the whole of Track A.
- **B2, C1 and C2 are days each.**
- **Phase 1 is months, not weeks.** Any plan implying otherwise should be treated as suspect.

**One clock to start immediately and separately:** Anthropic Scale tier is reached by usage history,
not payment (D138). A 5,000-endpoint fleet cannot go from zero spend to a large pilot — the history
has to accrue first. That is procurement lead time that costs nothing to start and cannot be bought
later.

## 7. Exit criteria — falsifiable

Phase 1 is done when all of these are true. Each is a test someone can run and fail.

**Track A**
1. The three `XFAIL` lines in `consent-surface.test.mjs` pass, and the demonstrated substitution is
   **refused and audited as a refusal with `consentRendered` on the record.**
2. The broker runs as a Windows Service under LocalSystem; the agent runs unprivileged; all four
   primitives execute across the pipe with consent.
3. An agent built against a different protocol version is **refused cleanly and the refusal is
   audited** — not a crash, not a silent degrade.
4. A single MSI installs both halves on a machine where the user has no local admin, and uninstalls
   cleanly leaving no service and no key material.
5. The device key is TPM-backed where a TPM exists, and the hub can see which devices are on the
   software-key fallback path.

**Track B**
6. A device enrolls, appears in the console, and **a revocation takes effect within the access-token
   lifetime** (5 minutes, D132).
7. A local admin account with TOTP can read audit for its own tenant and nothing else, and every
   admin action is on the record.
8. A conversational turn is proxied through the hub with per-tenant metering, and a spend cap
   actually stops it.
9. A ticket is filed, an IT alias receives email, and the audit record and the ticket reference each
   other.
10. **A KB article edit is retrievable on the next query with no restart and no redistribution** —
    D108's claim, tested.

**Track C — the product criterion**
11. **`04-TEAM-REVIEW` §9's A2 exit criterion: a non-technical person with a genuinely broken laptop
    gets fixed unassisted, three times out of five.** This is the team's own stated falsifiable
    criterion and it is the only one on this list that tests whether the product works rather than
    whether the software runs.
12. Deflection can be computed from real sessions across the four outcomes, broken down by category.

## 9. Recommended first week

1. **A0** — two-step consent in `InProcessBroker`. Unblocks Track A and closes the largest finding.
2. **C1 and C2** — file the threat model and the generic KB. Closes OPEN-5, costs hours, and stops

   nor effort can compress later.
6. **Chase the top-30 categories.** Six weeks. It does not block the build; it blocks knowing
   whether the build was the right one.
