## 1. THE ANSWER IN ONE PARAGRAPH

Closing the window no longer quits. It hides the window to the notification area; the hub link and
the ticket poll keep running; the tray icon says one of three things — nothing waiting, *needs you*,
or cut off — and quitting is a deliberate act from the tray menu. Start with Windows is a checkbox in
that menu, **on by default because Charles decided it**, and the OS wins if a user turns it off in Task
Manager. Nothing is ever spoken with no visible window, and an update that arrives with no visible
window is **held, not shown to a hidden renderer** — because the renderer's acknowledgement is what the
console reports as *seen* and what D290's auto-close clock arms on, and a screen nobody saw is not
"seen". The Friday/Tuesday scenario was run in the real Electron window and ends the way it should:
resolved with the window closed, the tray says *needs you*, the window opened from the tray shows the
resolution, and the hub's clock moves from the resolution's instant to the acknowledgement's.

## 2. WHAT WAS BUILT

### The pure module and the store (brief §2.1)

- **`client/src/main/presence.js`** — imports nothing from Electron. `presence({ visible, hub, unread,
  autostart, previous })` returns the icon, the tooltip, the menu, `speech: allowed | muted` and
  `deliver: show | hold`. `closeOutcome()` says what a close does (hide, never quit; the notice on the
  first one). `UpdateHold` is the queue of desk updates that arrived while nobody could see them; its
  count is what turns the icon to *needs you*.
- **`client/src/main/settings.js`** — the main process's own `settings.json` in userData, beside the
  profile and **not inside it** (D215's identity file has a different meaning). Two booleans:
  `openAtLogin` (default **true**, D294) and `firstCloseNoticeShown` (D296). `resolveAutostart({ stored,
  os })` is the whole OS-wins rule (D295) and returns `apply` / `store` / `why` so the log can say what
  happened.
- **`client/src/main/main.js`** — wires them and holds no policy: the single-instance lock and the
  `second-instance` handler; `close` → `preventDefault` → hide; `before-quit` sets `isQuitting`, which
  is the only condition under which a close proceeds; the tray built **before** the window (with
  autostart there may never be one); `--background` skips `createWindow()`; `tts:speak` refuses on
  `presence.speech`; the window's audio muted on hide; the Piper worker stopped on hide and started on
  show; held updates delivered on show **and only once the renderer has finished loading** (a `send`
  before that is dropped silently — the direct path holds on the same condition, which also closes a
  latent boot race). `window-all-closed` stops the voice and nothing else.
- **`client/src/main/tts-service.js`** — the worker can be stopped and started within one process: a
  replaced worker's late exit no longer marks the new one not-ready, `stop()` clears `ready` first, and
  a start still waiting on a worker that has since been killed resolves at once rather than at the
  30-second timeout. The renderer tracks every later `tts:ready` event, not only the boot one.
- **The icons** — `client/assets/tray/{idle,needs-you,unreachable}.png` at 16 and 32 px, generated by
  `npm.cmd run tray:build` (`scripts/build-tray-icons.mjs`, no image library) as the avatar manifest's
  own static forms: hollow, haloed, struck. Told apart by shape, not hue, because the manifest says hue
  is unreadable at 16 px on an unknown taskbar.

All as specified; the register rows carry the detail (§5.61). Two things the brief left to judgement:

## 4. HONESTY LEDGER

- **The tray MENU was not driven, and the two things behind it were therefore not seen: *Quit Matic
  Desk* ending the process, and the *Start with Windows* checkbox toggling.** On this Windows 11 build
  (26200) the notification-area overflow accepted an injected left click (the window opened three times
  that way) but ignored injected right clicks — `mouse_event`, then `SendInput` with absolute
  coordinates — and the Menu key with the icon focused. The Electron process logged no right-click at
  all, so the input never reached it. Promoting the icon to the taskbar through `NotifyIconSettings`
  did not take effect live, and the change was reverted. **The menu's contents are pinned headlessly
  (`presence.test.mjs` §1) and the click wiring structurally (§4); clicking it is Charles's, and it is
  two right-clicks.** The OS-wins rule was exercised by the Task Manager marker instead, which is the
  stronger test of D295 anyway.
- **`window.close()` from inside the page bypasses the close handler.** Closing over the DevTools
  Protocol that way took Chromium's own route: the window was destroyed without the `close` event
  firing, no hide, no notice. No user reaches that path (nothing in the renderer calls it), the X path
  was then driven properly through WM_CLOSE and behaved, and — worth recording — the process survived
  even the bypass: `window-all-closed` no longer quits. The next driver will try the same thing.
- **The stale hub on 8787 is still running the pre-D290 code with the insecure bypass ON.** It was
  started at 00:32 today; the D290 server commit is 02:15. This session could not stop it (the action
  was refused), so the click-through ran against a **second hub on 8790** from the current tree. The
  memory note's instruction stands: restart 8787 with `npm.cmd start` before any demo. Two hubs polled
  one job queue during the run; no `ticket.autoclose` job was due, so the old handler claimed nothing.
- **Start with Windows is now registered on Charles's development machine, by the founder's default,
  from the test profile** — `HKCU\…\Run\MaticDesk` → the repo's `electron.exe` with the app path and
  `--background`, enabled. At the next logon Matic Desk will start to the notification area under the
  DEFAULT userData (config.json: hub 8787, empty secret). That is the decided product behaviour; it is
  also one click to turn off in the tray menu, and this ledger is where it is written down. The
  `StartupApproved` marker the trap test wrote was removed afterwards, so Task Manager shows the entry
  enabled, matching the default.
- **`--user-data-dir` is what kept this run apart from the agent Charles has had running since
  02:45 on the default userData.** Without it the two would have shared a lock, a snapshot and an
  enrollment, and the older instance's visible window would have acknowledged the reply first.
- **Nothing was heard.** The voice was started and stopped with the window (the log says so; Piper's
  exit and ready lines bracket every hide and show) but no audio was listened to. The greeting after
  the tray click in step 16 will have been spoken to an empty room.
- **The tooltip reads back through UI Automation with a plain hyphen where the string has an em dash.**
  The log shows the em dash; the console codepage does not. Left as written.
- **The taskbar flash for a visible-but-unfocused window is unchanged and, as before, unobserved.**
- **Nothing here is a performance measurement.** The 30-second poll and the ~1-minute unreachable
  transition are the configured values, not findings.
